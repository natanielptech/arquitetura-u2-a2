FUNDAMENTOS

Uma linguagem para problemas recorrentes

Christopher Alexander descreveu padrões como problemas recorrentes em um contexto e o núcleo de uma solução. Em 1994, a Gang of Four organizou 23 padrões orientados a objetos em um vocabulário compartilhado.

01

Um rótulo curto para conversar sobre uma solução.

02

03

Solução

Uma estrutura de colaboração entre objetos.

04

Consequências

Os tradeoffs: flexibilidade, custo e complexidade.

Padrão não é código pronto. É uma estrutura de colaboração reconhecida por sua intenção — não pela forma exata do código.

CRITÉRIO DE APLICABILIDADE

O padrão resolve o problema — ou só adiciona peças?

1

Nomeie o problema

Descreva o que está difícil sem citar um padrão.

2

O problema já existe?

Se não se manifestou nem está claramente previsto, não antecipe uma abstração.

3

Compare aplicabilidade e custo

Avalie complexidade, desempenho e quantidade de classes.

4

Escolha a solução mais simples

Aplique o padrão e documente a decisão só se o benefício compensar.

Não se manifestou?Não aplique por precaução.
O custo supera o ganho?Resolva com o mais simples possível.

SINAIS NO CÓDIGO

Cheiros que podem apontar caminhos

Cadeia de condicionais por tipo→Strategy ou Factory Method
Combinações opcionais explodem em subclasses→Decorator
Vários componentes reagem ao mesmo evento→Observer

Um smell é uma pista para investigar, não uma ordem automática para aplicar um padrão.

EXEMPLO ADICIONAL · JAVA

Quando Strategy é over-engineering

✓ REGRA ESTÁVEL
BigDecimal calcularImposto(Pedido pedido) {
    return pedido.total().multiply(TAXA_PADRAO);
}

Uma implementação, sem variação prevista: mantenha simples.

× ABSTRAÇÃO PREMATURA
interface RegraImposto { ... }
class ImpostoPadrao implements RegraImposto { ... }
class Pedido { RegraImposto regra; }

Tipos e indireção sem um problema de variação: custo sem benefício.
